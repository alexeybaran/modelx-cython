# Cython: a chained comparison ignores an error raised by the truth test of its first link

## Summary

In a chained comparison such as `a > x not in y`, Python evaluates `a > x`, then tests that result for truth. If
the result is an object whose truth test raises (a NumPy array or a pandas Series of more than one element), Python
raises that error.

Code generated by Cython calls `__Pyx_PyObject_IsTrue()` on the first link's result and uses the return value
directly as a condition:

```c
__pyx_t_4 = __Pyx_PyObject_CompareGt_object_float(__pyx_t_1, __pyx_float_0_5, Py_GT); ...
if (__Pyx_PyObject_IsTrue(__pyx_t_4)) {
    __Pyx_DECREF(__pyx_t_4);
    ...   /* evaluates the next link */
}
```

The -1 error return is taken as true. Execution continues with the exception still set. The function then returns
a value while an exception is pending.

- **From a `def` function:** the interpreter turns this into `SystemError: ... returned a result with an exception
  set`.
- **From a `cdef` function returning `object`:** the caller can receive the value with no error at all.
- **Memory corruption:** in a larger module, the pending exception's traceback kept a frame whose local was released
  by the generated code. This gave a use-after-free, which valgrind reports and which ends in a segmentation fault
  during a later garbage collection.

## Reproduction

`shapes.pyx`:

```cython
def gt_not_in(a, x, y):
    return a > x not in y

def gt_in(a, x, y):
    return a > x in y

def gt_lt(a, x, y):
    return a > x < y

def eq_is(a, x, y):
    return a == x is y

def gt_not_in_if(a, x, y):
    if a > x not in y:
        return 'yes'
    return 'no'

def typed_gt_lt(double a, double x, double y):
    return a > x < y
```

Each function is called in a fresh process, with the same body evaluated by the interpreter as the reference:

```python
import numpy as np
arr = np.array([0.1, 0.9])
# gt_not_in(arr, 0.5, (1, 2)), gt_in(arr, 0.5, (1, 2)), gt_lt(arr, 0.5, 1.0), eq_is(arr, 0.5, None),
# gt_not_in_if(arr, 0.5, (1, 2)), typed_gt_lt(0.7, 0.5, 1.0)
```

`cythonize -i shapes.pyx`, CPython 3.13, NumPy 2.5:

| function | Python | Cython 3.2.4 | Cython 3.3.1 | Cython 3.3.2 |
|---|---|---|---|---|
| `a > x not in y` | ValueError | SystemError | SystemError | SystemError |
| `a > x in y` | ValueError | SystemError | SystemError | SystemError |
| `a > x < y` | ValueError | SystemError | SystemError | SystemError |
| `a == x is y` | ValueError | SystemError | SystemError | SystemError |
| `if a > x not in y:` | ValueError | SystemError | ValueError | ValueError |
| `a > x < y`, C doubles | True | True | True | True |

The defect is independent of the operator of either link. It appears whenever the first link's result is a Python
object. With typed C operands the first link is a C boolean, and the result is correct.

In an `if` test, 3.3.1 and 3.3.2 check the error. 3.2.4 does not.

A newer Cython than 3.3.2 has no wheel on PyPI, so the development branch was not tested.

## Through a `cdef` function

```cython
cdef object chained(a, x, y):
    return a > x not in y

def via_cdef(a, x, y):
    r = chained(a, x, y)
    return type(r).__name__
```

Cython 3.3.2 gives `SystemError: <cyfunction via_cdef> returned a result with an exception set`. Inside the module,
`r` is the array, and code between the call and the return runs as if no error had been raised.

## Expected

The truth test of the first link should be checked like any other:

```c
__pyx_t_9 = __Pyx_PyObject_IsTrue(__pyx_t_4); if (unlikely(__pyx_t_9 < 0)) __PYX_ERR(...);
if (__pyx_t_9) { ... }
```

Then the interpreter's ValueError propagates.
